# Knowledge Base Structure Rules

> Type: reference / Last reviewed: YYYY-MM / Owner: TBD

このファイルは、このナレッジベースの構造仕様の正本です。`AGENTS.md` は薄い地図です。

## 1. Design Principles

1. 主な読み手は agent である。
2. 地図と領土を分ける。
3. 安定した真実と、変化する現在の状態を分ける。
4. 重要な状態はスクリプトで検証しやすくする。

## 2. Directory Structure

```text
.
├── AGENTS.md
├── _core/
│   ├── 00-09_index/
│   └── 10-19_domain/
├── decisions/
├── projects/
├── areas/
├── resources/
└── archives/
```

## 3. Layer Rules

ドキュメントの置き場所は、次の順で判定する。

1. いつ・なぜその選択をしたかを説明する decision record か。該当するなら `decisions/` に置く。
2. 現在の projects がすべて終わっても有効か。該当するなら `_core/` に置く。
3. 明確な完了条件がある取り組みに紐づくか。該当するなら `projects/` に置く。
4. 継続的な責任領域か。該当するなら `areas/` に置く。
5. 再利用可能な参照情報か。該当するなら `resources/` に置く。
6. 完了・非アクティブになったものか。該当するなら `archives/` に置く。

## 4. Dependency Direction

許可:

- `projects/`、`areas/`、`resources/` は `_core/` と `decisions/` にリンクしてよい。
- MOC は、自分が索引する配下のファイルへリンクしてよい。

避ける:

- `_core/` が active な `projects/`、`areas/`、`resources/` に依存すること。
- 現行ファイルが `archives/` に依存すること。

## 5. Archives Rule

`archives/` は agent の探索対象から除外する。agent は archived material を grep・引用・現在の文脈として利用しない。

## 6. MOC Rules

MOC はコンテンツ本体ではなく地図である。

- Root MOC: `_core/00-09_index/00.00-moc.md`。
- Group MOC: `projects/<group>/AC.00-*-moc.md`、`areas/<group>/AC.00-*-moc.md`、`resources/<group>/AC.00-*-moc.md`。
- Root MOC は group MOC や代表的な入口へリンクし、すべての個別ファイルを列挙しない。
- 各 MOC は短く保つ。
- 状態を複製せず、詳細 note へリンクする。
- 全ファイル一覧が必要な場合は、手管理の MOC ではなく生成物または lint 出力として扱う。

## 7. Status Blocks

各 project / area MOC は、運用状態を示すセクションを次の形式で始める。

```markdown
## Status (Last updated: YYYY-MM-DD)

| Task | State | Due |
|---|---|---|
| Example task | 🟡 In progress | YYYY-MM |
```

状態:

- 🔴 Not started
- 🟡 In progress
- 🟢 Done
- ⏸ Paused

未完アクションは `- [ ]` を使う。完了したアクションは、履歴を残すため `- [x]` にする。

## 8. Meeting Notes And Task Intake

会議メモは input record であり、タスクの正本ではない。文字起こしや議事録からアクション・決定が出た場合、対象 project / area の文脈を読み込んでいないセッションでは、対象を直接編集しない。

ルール:

- 議事録には、会議で出たアクション・決定・背景を記録する。
- 追跡すべき作業は、会議を所有する project / area の MOC に「反映TODO」として `- [ ]` で置く。
- 反映TODOは、対象 project / area と「現在の文脈を読んでから反映する」前提が分かる文にする。
- 後続セッションが対象 project / area を読み込み、既存タスク・粒度・責任範囲・完了条件を把握した上で反映する。
- 議事録本文では原則 `- [ ]` を使わず、表や番号リストで記録する。
- 例外的に議事録自体をタスクソースにする場合だけ、冒頭に `<!-- kb-tasks:include -->` を置く。

例:

```markdown
- [ ] Reflect the 2026-07-05 meeting decision about API ownership into projects/10-19-example-project after reading its current context
```

## 9. Closure And Distillation Workflow

project が完了した、または area が自分・チームの継続責任ではなくなった場合は、すぐに丸ごと archive せず、先に再利用可能な知識を蒸留する。

対象:

- `projects/`: 完了条件を満たしたもの。
- `areas/`: 担当変更・組織変更・終了などにより、継続責任ではなくなったもの。
- `resources/`: 陳腐化・不要化したもの。必要なら更新し、不要なら archive する。

`_core/` と `decisions/` は原則 archive しない。古くなった decision は履歴として残し、必要なら新しい decision を追加する。

蒸留先:

- 安定したルール・定義 → `_core/`
- 横断的な意思決定 → `decisions/`
- 再利用可能な参照情報 → `resources/`
- 継続して残る責任領域 → `areas/`
- 残りの終了済み project / 非アクティブ area → `archives/`

手順:

1. 対象 MOC のステータスと最終更新日を更新する。
2. 再利用可能な知識を上記の蒸留先へ移す、またはリンクする。
3. root MOC と関連 MOC から、終了済み project / 非アクティブ area への現行リンクを外す。
4. 終了済み project / 非アクティブ area を `archives/` へ移動する。
5. `python3 tools/kb-tasks.py --write` でタスク集約を再生成する。
6. `python3 tools/check-links.py` でリンク切れを確認する。

## 10. Task Index

`_core/00-09_index/00.02-tasks.md` は次のコマンドで生成する。

```sh
python3 tools/kb-tasks.py --write
```

手で編集しない。

スキャン対象:

- `projects/` と `areas/` 配下の `*-moc.md`。
- `<!-- kb-tasks:include -->` を含む Markdown ファイル。

無視対象:

- `archives/` 配下のすべて。
- `AGENTS.md`。
- `<!-- kb-tasks:ignore -->` を含むファイル。

## 11. File Naming

- lowercase kebab-case を使う。
- `_core/`、`projects/`、`areas/`、`resources/` では Johnny.Decimal 風の prefix を使う。
- MOC には `AC.00-*-moc.md` を使う。
- `decisions/` と `archives/` では numeric prefix を使わない。
- 廃止した番号を再利用しない。
- 番号だけで曖昧になる場合は、path または MOC title で参照する。

### Optional: Numbering Scope

このテンプレートは、KB 全体でただ一つの番号体系を必須にしない。番号は agent と人間が安定して参照するための補助であり、使う人の認知負荷を下げる方式を選んでよい。ただし、同じ KB 内では番号の意味を一貫させる。

よくあるパターン:

- Bucket-scoped: `projects/`、`areas/`、`resources/` の bucket ごとに番号空間を分ける。小規模で気楽に始めやすい。
- Topic-scoped: 番号帯を KB 全体の主題に割り当て、同じ主題の project / area / resource が同じ番号帯を共有する。番号を見た瞬間に主題を理解しやすい。
- Domain-prefixed: 大規模な業務 KB やチーム KB で、`dev.`、`hr.`、`sec.` のような domain prefix を付ける。

### Optional: Domain-Prefixed Addressing

大規模な業務KBやチームKBでは、JD番号の枯渇を避けるためにドメインprefix付き番地を使ってよい。

形式:

```text
<domain>.AC.ID-name.md
```

例:

- `dev.31.01-aws-account-structure.md`
- `org.20.03-kb-lint-policy.md`
- `hr.40.00-recruiting-index.md`
- `sec.80.00-security-requirements-index.md`

ルール:

- prefix は知識ドメインを表す。
- PARA フォルダはライフサイクルまたは状態を表す。
- prefix と PARA フォルダは直交させる。同じ `dev` prefix のファイルが `_core/`、`areas/`、`projects/`、`resources/` のどこにあってもよい。
- `AC.ID` は prefix 内で一意であればよい。グローバル一意にはしない。
- prefix/category の割当は root MOC の registry で管理する。
- 小規模KBでは標準の `AC.ID-name.md` 形式を使い、必要になった時点でこのパターンへ移行する。

## 12. File Header

永続的なコンテンツファイルは、次のヘッダで始める。

```markdown
> Type: reference|explanation|how-to|tutorial / Last reviewed: YYYY-MM / Owner: Name
```

## 13. Links

ローカル Markdown link を優先する。本文中の相対パスが読みにくい場合は、好みに応じて reference-style link を使ってよい。

```markdown
See [example area][10.00-example-area].

<!-- links -->
[10.00-example-area]: ../../areas/10-19-example-area/10.00-example-area-moc.md
<!-- /links -->
```

コミット前にリンクチェックを実行する。

```sh
python3 tools/check-links.py
```

検証済みのまとまりになったら、こまめにコミットする。未コミットの変更を残して作業を終える場合は、理由と残っている変更を明示する。

## 14. Agent Workflow

このリポジトリで作業するときは、次の順に進める。

1. タスク索引を読む。
2. root MOC から関連する project または area を探す。
3. 現在のタスクに必要なファイルだけを読む。
4. 範囲を絞って編集する。
5. リンクチェックを実行し、タスク索引を再生成する。
6. 検証済みの変更をコミットする。未コミットで残す場合は理由を説明する。
7. 変更内容と検証上の残リスクを報告する。

# Knowledge Base Structure Rules

> Type: reference / Last reviewed: YYYY-MM / Owner: TBD

This file is the canonical specification for this knowledge base. `AGENTS.md` is only a short map.

## 1. Design Principles

1. The primary reader is an agent.
2. Keep maps and territory separate.
3. Separate stable truths from active state.
4. Make important state easy to validate with scripts.

## 2. Directory Structure

```text
.
├── AGENTS.md
├── _core/
│   ├── 00-09_index/
│   └── 10-19_domain/
├── decisions/
├── projects/
├── areas/
├── resources/
└── archives/
```

## 3. Layer Rules

Apply these checks in order when placing a document:

1. Is it a decision record explaining when and why a choice was made? Put it in `decisions/`.
2. Will it stay valid after all current projects end? Put it in `_core/`.
3. Is it tied to finite work with a clear end condition? Put it in `projects/`.
4. Is it an ongoing responsibility? Put it in `areas/`.
5. Is it reusable reference material? Put it in `resources/`.
6. Is it complete or inactive? Put it in `archives/`.

## 4. Dependency Direction

Allowed:

- `projects/`, `areas/`, and `resources/` may link to `_core/` and `decisions/`.
- MOCs may link downward to files they index.

Avoid:

- `_core/` depending on active `projects/`, `areas/`, or `resources/`.
- Any current file depending on `archives/`.

## 5. Archives Rule

`archives/` is excluded from agent exploration. Agents should not grep, cite, or use archived material as current context.

## 6. MOC Rules

MOCs are maps of content, not content bodies.

- Root MOC: `_core/00-09_index/00.00-moc.md`.
- Group MOCs: `projects/<group>/AC.00-*-moc.md` and `areas/<group>/AC.00-*-moc.md`.
- Keep each MOC short.
- Link to detailed notes instead of duplicating their state.

## 7. Status Blocks

Each project and area MOC should start its operational section with:

```markdown
## Status (Last updated: YYYY-MM-DD)

| Task | State | Due |
|---|---|---|
| Example task | 🟡 In progress | YYYY-MM |
```

States:

- 🔴 Not started
- 🟡 In progress
- 🟢 Done
- ⏸ Paused

Open actions must use `- [ ]`. Completed actions should use `- [x]` to preserve history.

## 8. Meeting Notes And Task Intake

Meeting notes are input records, not task sources of truth. When actions or decisions appear in a transcript or meeting note, do not directly edit a target project or area unless the session has loaded and understood that target context.

Rules:

- Record meeting actions, decisions, and background in the meeting note.
- Put trackable work in the meeting-owning project or area MOC as an intake TODO using `- [ ]`.
- Make the target project or area and the “read current context first” prerequisite explicit in the intake TODO.
- A later session should read the target project or area and reflect the work after understanding existing tasks, granularity, responsibilities, and completion criteria.
- Avoid `- [ ]` checkboxes in meeting notes by default; use tables or numbered lists instead.
- Use `<!-- kb-tasks:include -->` only when the meeting note itself is intentionally a task source.

Example:

```markdown
- [ ] Reflect the 2026-07-05 meeting decision about API ownership into projects/10-19-example-project after reading its current context
```

## 9. Closure And Distillation Workflow

When a project is complete, or an area is no longer an ongoing responsibility for you or your team, do not archive it wholesale before distilling reusable knowledge.

Targets:

- `projects/`: Work that has met its completion condition.
- `areas/`: Responsibilities that are no longer active because of ownership changes, organizational changes, or closure.
- `resources/`: Material that is stale or no longer needed. Update it if still useful, or archive it if not.

`_core/` and `decisions/` are normally not archived. Keep old decisions as history and add a new decision when needed.

Distillation targets:

- Stable rules or definitions -> `_core/`
- Cross-cutting decisions -> `decisions/`
- Reusable references -> `resources/`
- Ongoing responsibilities that remain active -> `areas/`
- Remaining completed projects or inactive areas -> `archives/`

Workflow:

1. Update the target MOC status and last-updated date.
2. Move or link reusable knowledge to the appropriate distillation target above.
3. Remove current links to the completed project or inactive area from the root MOC and related MOCs.
4. Move the completed project or inactive area to `archives/`.
5. Regenerate the task index with `python3 tools/kb-tasks.py --write`.
6. Check links with `python3 tools/check-links.py`.

## 10. Task Index

`_core/00-09_index/00.02-tasks.md` is generated by:

```sh
python3 tools/kb-tasks.py --write
```

Do not edit it manually.

Scanned files:

- `*-moc.md` under `projects/` and `areas/`.
- Any Markdown file containing `<!-- kb-tasks:include -->`.

Ignored files:

- Anything under `archives/`.
- `AGENTS.md`.
- Any file containing `<!-- kb-tasks:ignore -->`.

## 11. File Naming

- Use lowercase kebab-case.
- Use Johnny.Decimal-style prefixes in `_core/`, `projects/`, `areas/`, and `resources`.
- Use `AC.00-*-moc.md` for MOCs.
- Do not use numeric prefixes in `decisions/` or `archives/`.
- Do not reuse retired numbers.

### Optional: Domain-Prefixed Addressing

For larger team or business knowledge bases, use domain-prefixed addresses to avoid exhausting Johnny.Decimal number ranges.

Format:

```text
<domain>.AC.ID-name.md
```

Examples:

- `dev.31.01-aws-account-structure.md`
- `org.20.03-kb-lint-policy.md`
- `hr.40.00-recruiting-index.md`
- `sec.80.00-security-requirements-index.md`

Rules:

- The prefix represents a knowledge domain.
- The PARA folder represents lifecycle or state.
- Keep the prefix and PARA folder orthogonal. Files with the same `dev` prefix may live in `_core/`, `areas/`, `projects/`, or `resources`.
- `AC.ID` only needs to be unique within a prefix. Do not require global uniqueness.
- Maintain prefix/category assignments in the root MOC registry.
- For small knowledge bases, use the standard `AC.ID-name.md` format and migrate to this pattern only when needed.

## 12. File Header

Each durable content file should start with:

```markdown
> Type: reference|explanation|how-to|tutorial / Last reviewed: YYYY-MM / Owner: Name
```

## 13. Links

Prefer local Markdown links. If inline relative paths make body text hard to read, reference-style links are an optional readability pattern:

```markdown
See [example area][10.00-example-area].

<!-- links -->
[10.00-example-area]: ../../areas/10-19-example-area/10.00-example-area-moc.md
<!-- /links -->
```

Run link checks before committing:

```sh
python3 tools/check-links.py
```

Commit frequently once a verified change is coherent. If you end work with uncommitted changes, state why and list what remains.

## 14. Agent Workflow

When working in this repository:

1. Read the task index.
2. Use the root MOC to find the relevant project or area.
3. Read only the files needed for the task.
4. Make scoped edits.
5. Run link checks and regenerate the task index.
6. Commit verified changes. If anything remains uncommitted, explain why.
7. Report what changed and any verification gaps.
